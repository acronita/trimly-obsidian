# Architecture

## Encryption rule

Every file Trimly writes to the vault is encrypted. `src/store.ts` is the only module that calls
vault write APIs, and it only writes text produced by `encryptText`. `test/encryption-rule.test.ts`
scans `src/` and fails if any other module writes to the vault, if `store.ts` writes anything not
produced by `encryptText`, or if new fields are added to the settings (`data.json`).

## Source layout

| File | Role |
|---|---|
| `src/crypto.ts` | Web Crypto: PBKDF2 key derivation, AES-GCM encrypt/decrypt, envelope format. No Obsidian imports (unit tested in Node). |
| `src/ledger.ts` | Data model and pure finance logic: balances, credit card bills (`cardBill`: any bill by closing day, payments after a closing pay that bill and the excess goes to the next; installment purchases projected into open and future bills), month summaries, spending by category, recurring posting (and linking rules on synced accounts to the imported charges), obligations (open occurrences, reminders, settling, payment suggestions, automatic payment linking, card bills as obligations), transaction similarity (`matchScore`/`bestMatch`: shared description words first, then amount, then date — used by synced recurring rules and obligation payments), amount parsing; portfolio totals, snapshots (`recordSnapshot` rebuilds today's flows from known movements plus an accumulated untracked part) and manual positions/movements (`saveAsset`, `saveManualMovement`, …, which apply movements to value, cost at average cost, and quantity). No Obsidian imports. |
| `src/business-days.ts` | Brazilian bank calendar: weekends and national holidays (movable ones from Easter); `businessDayFrom` gives the day a payment marked on a closed day is scheduled for. No Obsidian imports. |
| `src/store.ts` | `EncryptedStore`: loads/decrypts and encrypts/saves the ledger file; caches the derived key; serializes writes; remembers its last write to ignore its own modify events. |
| `src/passphrase.ts` | `PassphraseManager`: passphrase in memory and, optionally, in vault-scoped `localStorage` (device app data, outside the vault). |
| `src/bank-sync.ts` | Pure merge of Pluggy data into the ledger: creates synced accounts, pairs own-account transfers (card bill payments, the card's side paired when categorized as any transfer, dropping the second copy of a paid bill some banks report on the card), stores each card's bill dates, imports the 12 months fetched (`SYNC_HISTORY_DAYS`) and reconciles the 90-day window (`SYNC_WINDOW_DAYS`: re-links transactions Pluggy re-created with a new id, at any date, and removes ones in the window it no longer returns), maps Pluggy categories, aligns balances. No Obsidian imports (unit tested in Node). |
| `src/investment-sync.ts` | Pure merge of Pluggy investment positions and their movements: upserts assets by Pluggy id, maps Pluggy type/subtype to an asset class, upserts movements (re-linking ones with a new id), closes positions an item stopped reporting (only for items whose investments loaded), records the day's portfolio snapshot with its flow and income since the previous day (from movements, or estimated from the amount invested for positions without them; a newly tracked position counts as money in). No Obsidian imports (unit tested in Node). |
| `src/pluggy.ts` | Minimal Pluggy HTTP client over Obsidian's `requestUrl`: auth, accounts per item, `GET /v2/transactions` with cursor pagination, `GET /investments` per item (plus `GET /items/{id}` for the connector name when a position has no institution) and `GET /investments/{id}/transactions` per position (paged; a failure is reported, not fatal), `GET /bills` per credit card (paged; a failure leaves the card on its closing and due days), category tree. Only called when bank sync is configured. |
| `src/i18n/` | Interface text: `pt-BR.ts` is the source dictionary (`Strings` is its type), `en.ts` its translation, `index.ts` the active dictionary `t` and `setLanguage()`. No Obsidian imports. |
| `src/quotes.ts` | Pure quote logic: which codes are B3 tickers, applying brapi quotes to positions (display on all, revaluing manual ones with a quantity and recording a snapshot). No Obsidian imports (unit tested in Node). |
| `src/brapi.ts` | brapi.dev client over `requestUrl`: `GET /api/quote/{ticker}?range=3mo&interval=1d` with a Bearer token, one ticker per request (history comes in the same response); a rejected token or rate limit stops the run, other failures are reported per ticker. |
| `src/charts.ts` | Dependency-free charts: donut (SVG), paired income/expense bars (HTML), time-proportional lines (SVG). |
| `src/returns.ts` | Pure returns math: time-weighted portfolio index from the snapshots (their recorded flow and income; older snapshots fall back to amount-invested changes), period and monthly returns, CDI/IPCA compounding. No Obsidian imports (unit tested in Node). |
| `src/fx.ts` | Frankfurter client over `requestUrl`: `GET /v1/latest?base=…&symbols=…` (ECB reference rates, no key); currencies the ECB does not publish are left out. Called from `TrimlyPlugin.refreshRates()` on unlock, after each sync and when the currency setting changes, at most once a day; the rates are stored in the ledger (`fx`). |
| `src/bcb.ts` | Central Bank of Brazil SGS client over `requestUrl`: CDI (series 12, daily) and IPCA (series 433, monthly); 404 = no values in range. Called from `TrimlyPlugin.benchmarks()`, which caches the result in memory for the day. |
| `src/modals.ts` | Passphrase (unlock/create/change), confirm, transaction (incl. linking it as an obligation payment), recurring, obligation, settle (mark an occurrence done/skipped), account, category, position (synced: name and class only) and manual movement editors. |
| `src/view.ts` | `TrimlyView` dashboard with an Accounts/Investments mode switch. Investments tabs: overview (portfolio hero, evolution chart, performance vs CDI/IPCA, allocation donut, by institution, largest positions, maturities), portfolio (positions by class, closed ones apart), performance (cumulative return chart, periods, month by month), movements (filterable, grouped by month), income (12-month totals, yield, per month, per position), targets (per-class target, gap to target, contribution planner). Clicking a position opens a details modal. Accounts tabs: overview (net worth hero, 6-month cash flow, spending donut, accounts, recent, upcoming), transactions (grouped by day), accounts, planning (*Planejamento*, tab id `budgets`: `monthPlan()` cascade planned vs actual, plan and actual donuts, category tiles as fixed costs plus an extra limit, investment goal), recurring (with subscriptions apart), obligations (a *A fazer* / *Cadastradas* switch: due in the next 30 days by overdue, 7 days and later, card bills and open-bill projections included, recently done folded; or everything registered), categories. Styles use container queries so it adapts to narrow panes. |
| `src/main.ts` | Plugin entry: unlock/lock flow, `mutate()` (change → re-render → encrypt → save), external-change reload, bank sync (`syncBank()`, auto on unlock), obligation reminders (`remind()`, on unlock and hourly while unlocked), settings tab. |
| `src/styles/index.css` | Styles, bundled by esbuild into `styles.css`. |

## Encrypted file format

`<folder>/ledger.trimly` is pretty-printed JSON:

```json
{
  "trimly": 1,
  "kdf": { "name": "PBKDF2", "hash": "SHA-256", "iterations": 600000, "salt": "<base64>" },
  "cipher": { "name": "AES-GCM", "iv": "<base64>" },
  "data": "<base64 ciphertext + GCM tag>"
}
```

The salt is generated on ledger creation and on passphrase change; the IV is new on every save.
The plaintext is the JSON of `Ledger` (`src/ledger.ts`):

- `version` — currently `5` (obligations set by day; `4` added obligations, `3` investments). Older plugin versions refuse newer ledgers instead of dropping fields they don't know.
- `accounts[]` — `id, name, type, openingBalance, archived?, pluggyId?, closingDay?, dueDay?, billDates?, creditLimit?, currency?` (`closingDay`: the bank's closing day, whose charges already go to the next bill. `billDates`: `{ close, due }[]`, the bank's own dates of each bill of a synced card, which win over `closingDay`/`dueDay` for their month. `pluggyId`: set on accounts created by bank sync; their opening balance is recomputed on each sync so the balance matches the bank. `currency`: ISO code of the account's money, from Pluggy's `currencyCode`; missing = the currency in the settings)
- `categories[]` — `id, name, kind (expense|income), color, icon?` (Lucide icon name; default categories get theirs back on load)
- `transactions[]` — `id, date (YYYY-MM-DD), type (expense|income|transfer), amount, accountId, toAccountId?, categoryId?, description, notes?, recurringId?, obligationId?, pluggyIds?, pending?, original?, installment?, billMonth?` (`billMonth`: synced card charges, the month (YYYY-MM) the bill holding the charge closes in, from Pluggy's `billForecastDate`, plus one month per installment after the 1st when a later installment carries the purchase's month (Rico; Nubank gives each its own); `cardBill` counts charges by `chargeBillMonth` (this, else the first closing after the date) and payments by date; `installment: { number, total }`: a card purchase in installments, set by bank sync from Pluggy's `creditCardMetadata` or a mark at the end of the description, or by the transaction modal on cards that are not synced; installments still to come are not stored but projected by `futureInstallments`, one per bill after the bill of the latest charge of the purchase (dated on the day each bill opens, its previous closing, so a moving closing day never skips or doubles a bill), grouped into purchases by description without the mark and count, each charge continuing the purchase whose latest installment comes closest before it; projected installments carry the `month` their bill closes in and are dated on the day it opens; `postDueInstallments` posts the due ones on cards that are not synced; `CardBill.planned` adds the projected ones to their bills, closed ones included, since some banks only report the first installment; `pluggyIds`: the one or two Pluggy transactions an imported entry represents; `amount` is in the account's currency; `original: { currency, amount }` is set when the transaction was made in another currency — a card purchase abroad — and `amount` is then what the account was charged, Pluggy's `amountInAccountCurrency`, or a conversion with the stored rates when Pluggy has none)
- `budgets[]` — `categoryId, limit`: category limits from before plans were kept per month; the plan of any month before the first in `plans`
- `categoryRules?` — `key, categoryId`: categories the user taught by changing a transaction's (`applyCategory()`); `key` is `descriptionKey()` of the description (words without accents, digits or generic bank wording). Bank sync gives new transactions the rule's category before mapping Pluggy's (`ruleCategory()`). Optional field, ledger version unchanged.
- `plans?` — `{ "YYYY-MM": { budgets[], investmentGoal? } }`: each month's plan in Planning. `budgets` are the day-to-day limits per category, on top of the category's bills (expense rules and payment obligations in it); `investmentGoal` is cents to invest, tracked by the month's `buy` movements (`contributionsInMonth()`), not expenses. A month without its own plan uses a copy of the latest earlier one (`budgetFor()`); editing a month (`editBudget()`) saves its own copy, so earlier months keep theirs as history. Income and bills planned still come from today's rules and obligations. Optional field, ledger version unchanged.
- `recurring[]` — `id, description, type, amount, accountId, toAccountId?, categoryId?, frequency, startDate, nextDate, endDate?, subscription?`. A rule on a synced account (one with `pluggyId`, while bank sync is configured) is never posted: `postDueRecurring` links the imported transaction closest to `nextDate` (within 7 days; same name and amount within 50%, or amount within 20%; generic bank wording such as "Transferência Recebida" or "Pix" is not a name) by setting its `recurringId` and category, and the rule takes that charge's amount. With no charge 7 days after the due date (counted up to the last sync), the occurrence is skipped.
- `obligations[]` — `id, name, kind (payment|document), frequency (monthly|yearly), day, endDay?, month?, endMonth?, since, archived?, amount?, remindDays, notes?, settled[], payee?, fixed?, categoryId?`; each settlement is `due, status (done|skipped), date, transactionId?`. No years are typed: each month (or, for yearly ones, each year) has one occurrence, due on `day` for payments and on `endDay` (the end of the window that opens on `day`) for documents, clamped to the month's last day. Yearly ones put `day` in `month`; a yearly document's window may end in a later `endMonth` (IRPF: March 23 to May 29). `since` is the first day of the month (yearly: of the year) it was created in, so what was already done that period can be recorded; occurrences due earlier never open; `archived` stops new and open occurrences. A payment marked done on a weekend or national bank holiday (`src/business-days.ts`, movable ones from Easter) gets the next business day as its `date`, and shows as scheduled until then. Ledgers from version 4 had `startDate`/`endDate`: on load the day (and month) come from `startDate`, `since` = `startDate`, a past `endDate` archives it and weekly ones become monthly. An occurrence is open until a settlement exists for its period (its month for monthly obligations, its year for yearly ones, so moving the due day doesn't reopen past ones). Obligations move no money by themselves. `payee` is the description of the last transaction linked as the obligation's payment; on unlock, bank sync and saving a transaction, open occurrences (due up to 15 days ahead) of obligations with a `payee` are linked to the unlinked outgoing transaction, up to today and within 15 days of the due date, sharing a word with it (`linkObligationPayments`); occurrences marked done by hand without a transaction get one the same way, without changing `payee` or `amount`; a bill with linked payments but no `payee` learns the latest one's description first. `fixed` puts a payment with the fixed costs in Planning (`monthPlan()`), else with the variable bills; `categoryId` puts its monthly amount in that category's committed part, and is taken from the first linked payment's category when unset. Two levels link a bill to its payments: a transaction's `obligationId` says which bill it pays, in any month (`tagBillPayments`, run with `linkObligationPayments`: payments linked to an occurrence, plus unmarked outgoing transactions sharing a word with the bill's name, `payee` or linked payments, without a different category, within 50% of its expected amount or, when none is known, in the bill's category, so payments from before the bill was registered count too; `null` = unlinked by hand, never matched again), and a settlement's `transactionId` says which occurrence it paid. Planning counts a transaction as its bill's by `obligationId`. It is an optional field, so the ledger version did not change. Linking a payment also sets `amount` to its amount; `expectedAmount` projects a payment at `amount`, else its last linked payment, else 0. Credit card bills are not stored as obligations: `cardBillObligations` builds one per card with a `dueDay` for the last closed bill while something is left to pay (paying it, a transfer into the card, takes it off) and one `projected` for the open bill at what was charged so far (never reminded of).
- `investments` — `assets[]`: `id, name, assetClass (fixed_income|treasury|stock|reit|etf|fund|retirement|other), code?, issuer?, institution?, quantity?, value (net, after taxes), grossValue?, invested?, rate?, rateType?, fixedRate?, dueDate?, updatedAt, closed?, pluggyId?, pluggyItemId?, movementsSynced?, addedOn?, subtype?, pluggyName?, renamed?, institutionEdited?` (no `pluggyId` = manual; sync replaces `name` with a readable one until `renamed`); `snapshots[]`: `date, value, invested, flow?, estimated?, income?`, oldest first, one per day, written on every sync (`flow`: net money in since the previous day's snapshot, `estimated`: the part movements don't explain — amount-invested estimates, newly tracked, closed or deleted positions — `income`: payouts in that window); `movements[]`: `id, assetId, date, type (buy|sell|income|tax|amortization|transfer), amount (net of fees), quantity?, description?, direction? (transfers: in|out), cost? (manual withdrawals: cost taken off), pluggyId?`; `targets[]`: `assetClass, pct` (percent; `rebalance()` scales them to 100%). Net worth for a past date uses the last snapshot on or before it (zero before the first one).
- `brapi?` — `token, lastUpdate?`: quote settings, encrypted like the Pluggy credentials. Positions with a B3 ticker carry `quote?: { price (cents), changePct?, time?, longName?, low52?, high52?, pe?, eps?, marketCap?, logo?, history? }` (`history`: last 3 months of daily closes, `[YYYY-MM-DD, cents]`).
- `fx?` — `base, date, fetched, rates`: exchange rates (units of each currency per 1 `base`, the settings' currency) used to convert other currencies in totals (`toBase()`: net worth, month summaries, spending by category, recurring totals). Dropped and fetched again when the currency setting changes; without a rate, amounts are left unconverted.
- `pluggy?` — bank sync credentials: `clientId, clientSecret, itemIds[], lastSync?`. Lives here, encrypted, so it is never in `data.json` and follows the vault to other devices.

All amounts are positive integer cents (`type` gives the direction; opening balances may be negative).

## Lifecycle

1. Opening the dashboard (or any command) calls `unlock()`. If a remembered passphrase decrypts the
   file, it opens silently; otherwise a passphrase modal asks for it. With no file yet, the create
   modal sets a passphrase and writes a starter ledger.
2. After decrypting, due recurring occurrences are posted and saved. If bank sync is configured and
   the last sync is older than 6 hours, a sync runs in the background; after each sync, rules on
   synced accounts are linked to the charges just imported.
3. Every edit goes through `plugin.mutate()`, which re-renders and re-encrypts the whole ledger.
4. If the file changes on disk from outside (sync, `git pull`), it is reloaded with the in-memory
   passphrase. Concurrent edits on two devices are last-write-wins.
5. **Lock** drops the decrypted ledger, the derived key and the in-memory passphrase.

## Build

`esbuild.config.mjs` bundles `src/main.ts` → `main.js` and `src/styles/index.css` → `styles.css`.
`scripts/copy-to-vault.mjs` copies the three plugin files into `OBSIDIAN_PLUGIN_DIR` from `.env.local`.
